# V2 / V3 各10回比較

実験日: 2026-08-19

## 問い

35 Hzのlocal左右追尾を残してLLMが一発ずつ撃つV2と、WAIT / LEFT / RIGHT / FIREの4 Cloud Agentが全操作するV3は、同じ15秒ViZDoom条件でどれだけ違うか。

## 条件

- model: `meta-llama/llama-3.1-8b-instruct`
- provider: OpenRouter経由Groq、fallbackなし
- scenario: `defend_the_center`
- duration: 15秒。死亡時はその場で終了
- paired seed: 7〜16
- 実行順: pairごとにV2先行 / V3先行を交互にした
- V2: `direct-bit + direct-aim-assist`、3 lane、FIRE鮮度300 ms
- V3: `four-agent`、8 lane、旋回lease 600 ms、FIRE鮮度400 ms
- worldは推論中も35 Hzで進行
- startup probe失敗は再試行して別記録にする予定だったが、20本すべて初回通過

## 何がネックだったか

### 1. 29 msのlatency差だけでは説明できない

V3のrun平均選択はV2より約29.2 ms遅いだけだが、平均killは72.2%減った。主因はCloudの絶対速度より制御方式にある。

V2はLLM待ち中でもlocal spineが最新の敵位置を35 Hzで読み、毎tick LEFT / RIGHTを更新する。V3は約0.28秒前の位置を見たAgentが短い旋回leaseを出す。返答が来る頃には敵も照準も動いており、古い方向を数tick維持して通り過ぎる。

### 2. 身体が止まる

WAIT比率はV2の35.2%からV3の60.2%へ増えた。V2は敵がいなければlocal spineが連続探索するが、V3はRIGHT Agentの新鮮なleaseがない区間で全ボタンを離す。探索と追尾が途切れ、発砲可能な中央観測そのものが減った。

### 3. 4人分の大半を捨てる

V3は1観測4 request、さらに2世代pipelineである。1,348 game requestのうち、464票は到着時に最新世代ではなく棄却された。これは安全には必要だが、rate limit・費用・provider queueを消費してから捨てている。

### 4. 発砲判断も古い

V3は30 FIRE tickで28発を実際に消費し、15 hit。V2は71 FIRE tick、62発消費、54 hitだった。V3はFIRE Agentが正しく中央を見ても、実行時には敵が中央を外れている。FIREをlocal再確認しない公平な設計なので、このmissはそのまま成績になる。

### 5. 黒板はまだ協調に使えていない

V3は前ラウンド票を全Agentへ注入するが、現在の8B baselineでは無視させている。読ませるとLEFT / FIREが全員0になる実験があった。したがって現在のV3は4人の相談というより、4専門classifierの非同期競争である。

## 結論

V3は「4 Cloud LLMだけで全操作できる」ことを再現したが、性能では10 / 10でV2に負けた。今の最重要改善はLLMをさらに速くすること単独ではなく、Cloud Agentが古い座標から長いLEFT / RIGHTを出す方式をやめること。

次候補は、Agentが方向ではなく短い角速度と予測時刻を返す、到着時刻からではなく敵の運動予測でleaseを補正する、またはLEFT / RIGHT Agentだけを安価なlocal視覚policyへ落とさずCloud上で高速・常駐化すること。黒板より先に「身体が60%止まる」を直す方がkillへ効く。
