# V3: 四人制運動野（Four-Agent Blackboard）

## 一言

Cloud LLMを `WAIT / LEFT / RIGHT / FIRE` の4人に分け、全員へ同じDoom観測と前回の相談結果を渡して、ゲームを止めずに操作させる。

## 何が変？

普通は一つのAgentが「見る・考える・動く」を全部担当する。V3では、各Agentは一種類の動きしか提案できない。

- WAIT Agent: 何もしない担当
- LEFT Agent: 左旋回担当
- RIGHT Agent: 右旋回担当
- FIRE Agent: 発砲担当

各Agentの返事は一文字だけである。

- `1`: 今は自分の動きだ
- `0`: 今は自分の動きではない

同じ観測に対する4リクエストを同時にCloudへ送り、最初に届いた新鮮な `1` を身体が採用する。優先度は `FIRE >>> WAIT = LEFT = RIGHT`。同格の3種は先着勝ちとし、LEFT/RIGHTが競合しても途中で反転させない。同じ観測のFIREだけは後着でも既存選択を上書きできる。旋回とWAITは短い期限付き操作、FIREは必ず一発で消費する。何も有効な提案が来なければWAITする。

## 共有黒板

4人は同じAPI生成の途中へ相互に文字を注入できない。そのため、現在ラウンドの返答を現在ラウンドの仲間へ見せることはできない。

代わりに、次の観測へ「前ラウンドで各Agentが0/1のどちらを返し、身体が何を実行したか」を黒板として添付する。

```text
current: v=1 x=-231 a=37 h=84
previous: o=12 p=0100 e=L
```

`p`の並びは `WAIT / LEFT / RIGHT / FIRE`。小型モデルが役名に引っ張られないよう、実際のpromptでは黒板をこの圧縮表現にする。

送信開始順だけは優先度に合わせて `FIRE / WAIT / LEFT / RIGHT` とする。アプリ上は同時起動でもprovider内部で同時実行数が絞られる場合があるため、FIREを待ち行列の先頭へ置く。黒板のビット順は変えない。

つまりこれは完全な同時会話ではなく、ゲームのフレームをまたいだ遅延共有メモリである。

## ローカル側がしてよいこと

ローカル側は次だけを行う。

1. Doomの状態を数値へ変換する
2. 4人へ同時送信する
3. 一文字目の0/1を読む
4. 観測番号と期限を検査する
5. 有効な提案をDoomのボタンへ変換する

敵の位置からLEFT/RIGHT/FIREをローカルで選んではいけない。狙いと射撃の決定主体は4つのCloud LLMである。

## 最初の実験用ポリシー

V3の通信と制御を公平に測るため、最初は正解が一意になるルールを4人へ共通で渡す。

```text
targetなし                 -> RIGHT
targetあり、ammoなし       -> WAIT
targetが照準より左         -> LEFT
targetが照準より右         -> RIGHT
targetが照準中央、ammoあり -> FIRE
```

自由な作戦会議は次段階にする。まず「4人が競合せず、動いている世界をCloud越しに操作できるか」を測る。

## 安全装置

- 応答はリクエスト自体に観測番号と担当動作が結び付いている
- 最初の非空白文字以外は操作に使わない
- 古い観測の提案は拒否する
- 旋回は期限切れで自動解放する
- FIREは一回の提案につき一発だけ
- FIREは鮮度期限内に受理された後、次の35 Hz tickへ載せるため最大50 msだけ実行猶予を持つ
- API障害、変な文字、無応答はWAITへ倒す
- 実験場所はViZDoomのローカル練習場だけ

## 面白いところ

これは「賢い一人の脳」ではなく、四人の極端に職務分掌されたCloud LLMが、遅い共有黒板を見ながら一つの身体を奪い合う仕組みである。分散システムとしてはわりと真面目なのに、会議の議題が毎回「右を向く係の出番か？」だけなのが妙にくだらなくてよい。
